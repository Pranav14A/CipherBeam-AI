# CipherBeam-AI — Android Optical Receiver

The Android Receiver is the camera-based receiving component of **CipherBeam-AI**, an offline optical communication system.

It uses the smartphone's camera to detect modulated **red and green LEDs** generated by an ESP32-S3 transmitter and reconstruct the transmitted message in real time.

The current implementation successfully receives and decodes:

```text
ESP32-S3 → Red/Green LEDs → Android Camera → Signal Processing → Optical Decoder → Message
````

The first successful end-to-end message received by the Android application was:

```text
HELLO
```

# 6. Optical Communication Protocol

The current receiver follows a simple deterministic optical protocol.

The protocol uses two physical optical channels:

```text
GREEN = CONTROL / FRAMING
RED   = DATA
```

The red and green LEDs are never intentionally ON at the same time.

---

# 7. Frame Structure

The current frame is:

```text
IDLE
  ↓
GREEN START
  ↓
START GUARD
  ↓
RED DATA
  ↓
END GUARD
  ↓
GREEN END
  ↓
IDLE
```

More precisely:

```text
GREEN ON      → 600 ms
GREEN OFF     → 200 ms
RED DATA      → 8 bits per character
RED OFF       → 200 ms
GREEN ON      → 600 ms
GREEN OFF     → IDLE
```

---

# 8. Timing Constants

Current optical timing:

```text
GREEN_START_DURATION = 600 ms
GREEN_END_DURATION   = 600 ms
GUARD_DURATION       = 200 ms
BIT_DURATION         = 200 ms
```

Therefore:

```text
1 optical bit = 200 ms
```

At approximately 25–30 camera frames per second, one bit is represented by several camera frames.

For example:

```text
200 ms ≈ 5–6 camera frames
```

This allows the receiver to use multiple observations to determine whether a bit is ON or OFF.

---

# 9. Data Encoding

The current protocol uses:

```text
8-bit ASCII
MSB first
```

For example:

```text
H = 0x48
  = 01001000
```

Therefore the red LED transmits:

```text
0 → RED OFF
1 → RED ON
```

For:

```text
HELLO
```

the transmitted bytes are:

```text
H = 01001000
E = 01000101
L = 01001100
L = 01001100
O = 01001111
```

Total:

```text
5 characters × 8 bits
= 40 bits
```

At 200 ms per bit:

```text
40 × 200 ms
= 8 seconds
```

The complete optical frame also contains the start guard and end framing signals.

---

# 10. Receiver State Machine

The optical decoder is implemented as a state machine.

Current states:

```text
WAITING_FOR_START
        ↓
START_DETECTED
        ↓
WAITING_FOR_DATA
        ↓
RECEIVING_PAYLOAD
        ↓
MESSAGE_COMPLETE
```

---

# 11. WAITING_FOR_START

Initially, the receiver waits for the green control signal.

The receiver does not immediately trust a single green detection.

Instead, multiple consecutive green samples are required.

Current confirmation requirement:

```text
GREEN_CONFIRM_SAMPLES = 3
```

Conceptually:

```text
Green
Green
Green
  ↓
START_DETECTED
```

This reduces accidental triggering from camera noise.

---

# 12. START_DETECTED

Once the green start signal has been confirmed, the decoder waits for the green LED to turn OFF.

The falling edge of the green signal acts as the synchronization reference for the data section.

After green turns OFF:

```text
200 ms START GUARD
```

is expected before the first red data bit.

---

# 13. WAITING_FOR_DATA

The decoder waits for the beginning of the red data section.

Once the guard period has elapsed, red samples are interpreted as data.

The receiver does not interpret red OFF as the end of a message.

This is important because:

```text
RED OFF = binary 0
```

Therefore the end of the payload is identified using the green control signal.

---

# 14. RECEIVING_PAYLOAD

During payload reception:

```text
RED ON  → 1
RED OFF → 0
```

The decoder divides the signal into:

```text
200 ms windows
```

For each window, the receiver determines the majority state.

For example:

```text
Camera samples during one 200 ms window:

ON
ON
ON
OFF
ON

Majority = ON

Decoded bit = 1
```

Similarly:

```text
OFF
OFF
ON
OFF
OFF

Majority = OFF

Decoded bit = 0
```

---

# 15. ASCII Reconstruction

The decoder collects eight bits at a time.

Example:

```text
01001000
```

is reconstructed as:

```text
H
```

Then:

```text
01000101
```

becomes:

```text
E
```

and so on.

The resulting message is validated as printable ASCII.

---

# 16. GREEN END Detection

The green LED is used to signal the end of the transmission.

When green becomes active during payload reception, the receiver treats it as the end-of-frame signal.

The final red OFF period before the green end signal is handled as the end guard.

The decoder then attempts to reconstruct the complete message.

---

# 17. Signal Processing

The receiver does not directly use raw RGB values.

CameraX provides YUV image data.

The implementation uses the chroma information from the image to estimate red and green dominance.

The receiver calculates:

```text
Red score
Green score
```

using the U/V chroma components.

The red score is based on:

```text
(V - U) / 255
```

while the green score uses:

```text
(U - V) / 255
```

The resulting values are clamped to:

```text
[-1, +1]
```

---

# 18. Region of Interest

Processing the entire camera image would be unnecessary and computationally expensive.

The receiver therefore focuses on a central region of the camera frame.

The current implementation uses approximately:

```text
Center 40% × 40% ROI
```

This reduces processing overhead and focuses detection on the expected LED region.

---

# 19. Signal Tracking

The receiver uses adaptive signal trackers for red and green.

The trackers maintain:

```text
Baseline
Envelope
Threshold
ON/OFF state
```

This allows the system to adapt to changes in ambient lighting.

The tracker contains parameters such as:

```text
baselineAlpha
attackAlpha
releaseAlpha
thresholdOffset
```

The current physical testing required immediate response behavior for the optical transitions, so the red and green trackers were configured with:

```text
attackAlpha = 1.0
releaseAlpha = 1.0
```

This prevents additional smoothing delay from shifting the optical timing.

---

# 20. Camera Analyzer

The `RedLedAnalyzer` performs the main per-frame image analysis.

Despite its historical name, it currently handles both:

```text
RED detection
GREEN detection
```

The analyzer:

1. Receives a CameraX `ImageProxy`
2. Reads the YUV planes
3. Determines the chroma region
4. Samples the central ROI
5. Calculates average U/V values
6. Calculates red score
7. Calculates green score
8. Updates red signal tracker
9. Updates green signal tracker
10. Sends timestamped optical samples to the decoder
11. Sends debug information to the UI

The decoder therefore receives:

```text
timestamp
redOn
greenOn
```

for every analyzed camera sample.

---

# 21. Why RedLedAnalyzer Handles Green Too

The analyzer is named `RedLedAnalyzer` because it originated from the red-data receiver implementation.

The current implementation intentionally keeps red and green analysis together because both signals originate from the same camera frame and use the same ROI/chroma processing pipeline.

Therefore:

```text
RedLedAnalyzer
      │
      ├── Red Signal Tracker
      │
      └── Green Signal Tracker
```

A separate `GreenAnalyzer` is not currently required.

# 25. Major Problems Encountered During Development

The receiver required several rounds of physical debugging.

The following issues were encountered during development.

---

## Issue 1 — Green Start Was Detected, But Message Never Completed

### Symptom

The receiver successfully detected:

```text
GREEN START
```

and entered the receiving state.

However, when the transmitter reached:

```text
GREEN END
```

the decoder sometimes remained in:

```text
RECEIVING_PAYLOAD
```

instead of completing the message.

### Cause

The final red OFF guard was not always finalized before the green end signal was processed.

The decoder had accumulated the red windows but had not necessarily committed the final red window before seeing green.

### Solution

When green is detected during payload reception, the decoder explicitly finalizes the current red window using:

```text
redOn = false
```

before completing the transmission.

This allows the final red OFF guard to be included correctly.

---

# 26. Issue 2 — 40 Windows Became 39 Data Bits

### Symptom

The decoder reported:

```text
completedWindows=40
```

but the implementation initially removed one window before decoding.

This resulted in:

```text
39 bits
```

which cannot form a complete number of 8-bit ASCII characters.

### Cause

The decoder was originally assuming that one of the completed windows always represented an extra trailing window.

That assumption was incorrect for the current protocol.

### Solution

The completion logic was changed to inspect the actual number of completed windows.

If the count is divisible by 8:

```text
40 % 8 == 0
```

all windows are treated as data.

If there is exactly one additional window:

```text
41 % 8 == 1
```

the extra window can be treated as the guard window.

Invalid counts are rejected.

---

# 27. Issue 3 — Decoder Received 40 Bits, But They Were Wrong

### Symptom

The decoder successfully received:

```text
40 windows
```

but the decoded bit stream was:

```text
10010000
10001010
10011000
10011000
10011110
```

which corresponds to invalid printable ASCII.

### Expected

The transmitter was sending:

```text
01001000
01000101
01001100
01001100
01001111
```

### Investigation

Comparing the two sequences revealed that the received sequence was effectively shifted by one bit.

Expected:

```text
01001000 01000101 01001100 01001100 01001111
```

Observed:

```text
10010000 10001010 10011000 10011000 10011110
```

The received data corresponded to the expected stream shifted left by one position, with a trailing zero.

This showed that the issue was not ASCII reconstruction itself.

The problem was optical timing/synchronization.

---

# 28. Issue 4 — Signal Tracker Smoothing Shifted Optical Timing

### Symptom

The red optical signal was physically transmitting at the correct timing, but the camera receiver's logical ON/OFF transitions were not always aligned closely enough with the actual LED transitions.

Because the signal tracker used attack/release smoothing, a transition could be delayed.

With a bit duration of only:

```text
200 ms
```

even a relatively small delay becomes significant.

### Solution

The red signal tracker was configured for immediate response:

```text
attackAlpha = 1.0
releaseAlpha = 1.0
```

This reduced signal-transition latency.

After this change, the decoded stream became significantly more stable.

---

# 29. Issue 5 — Green Signal Timing Also Required Immediate Response

The same principle applied to the green framing signal.

The green signal determines:

```text
START
END
```

and therefore directly controls the decoder state machine.

If green detection is delayed, the data synchronization point can move.

The green tracker was therefore also configured with:

```text
attackAlpha = 1.0
releaseAlpha = 1.0
```

This removed additional smoothing latency from the green framing channel.

---

# 30. Issue 6 — False Optical Start/End Events

During testing, the decoder occasionally reported very large numbers of windows such as:

```text
completedWindows=441
```

or:

```text
completedWindows=92
```

instead of the expected:

```text
40
```

### Cause

These events were caused by false optical framing detections.

The camera can observe changes in brightness and color caused by:

* Ambient light
* Camera auto exposure
* Reflections
* Background objects
* LED intensity changes
* Camera noise

A false green detection could cause the decoder to enter a receiving state even when a real transmission was not occurring.

### Current Mitigation

The receiver requires multiple consecutive green samples before accepting a green start signal:

```text
GREEN_CONFIRM_SAMPLES = 3
```

This provides basic noise rejection.

Further robust synchronization and signal filtering are planned for later phases.

---

# 31. Issue 7 — Red OFF Cannot Mean End of Message

An important protocol design issue was identified during implementation.

Because:

```text
RED OFF = bit 0
```

the receiver cannot determine the end of the message simply because the red LED turns OFF.

For example:

```text
01000000
```

contains multiple OFF periods.

Therefore, a separate framing mechanism is required.

### Solution

The green LED was assigned as the control/framing channel.

The final sequence is:

```text
RED DATA
   ↓
RED OFF / END GUARD
   ↓
GREEN ON
   ↓
GREEN OFF
```

This makes message completion unambiguous at the current protocol level.

---

# 32. Issue 8 — Camera Analysis and UI Must Not Be Coupled

The camera analyzer operates continuously and can generate many samples per second.

Updating the UI directly from every camera frame can create unnecessary work on the main thread.

### Solution

The architecture keeps the optical analysis and decoder processing inside the camera pipeline while UI state is updated separately.

The decoder snapshot is posted back to the UI thread for display.

This keeps the camera analysis path independent from the Compose UI.
